# Running, timing and profiling the tests

## Running

`tools/test.sh` is the one list of the engine's tests: `just test` runs it, the pre-push hook runs `tools/test.sh fast` (`.pre-commit-config.yaml`), and CI runs named groups of it (`.github/workflows/test.yml`).

- `tools/test.sh` runs every `tests/test_*.lua` under texlua, then `tests/test_bake.py`, `tests/test_lint.py`, `tests/test_tools.py` and `tests/test_tools_matrix.py`. One at a time it stops at the first failure.
- `tools/test.sh fast` runs the tests meant to finish in seconds; `tools/test.sh mix layout` runs the ones named (a name is the file's, without `test_` and `.lua`).
- `-j` and `--times` need `/usr/bin/time` and Python (`FLORA_PYTHON`, else `python3`): the tests run in a process group of their own, which Python makes and stops, since a shell without a terminal cannot (dash, `/bin/sh` on Ubuntu, turns job control off).
- When something goes wrong the runner says so rather than measuring wrongly: a bad option, a test named twice or a `--times` file that cannot be written stop it before any test starts (exit status 2); interrupted (Ctrl-C, TERM, HUP) it stops every test it started and writes no times (exit status 130, 143, 129).
- `-j N` runs N tests at a time. Each test's output is printed whole when it ends, every test runs, and the failures are named at the end. `-j auto` is half the processors the system has online, as `getconf _NPROCESSORS_ONLN` counts them on macOS and Linux alike: logical processors, so on a Linux machine with hyperthreading each core counts twice, and on Apple silicon (no hyperthreading) logical and physical are the same. At least one. A test file runs in one process however many jobs there are, so the wall time is never less than the slowest file's.
- `just test` is `tools/test.sh -j auto`; `just test 6` runs six at a time, and `just test 1` one at a time, stopping at the first failure. The pre-push hook and CI call `tools/test.sh` without `-j`, one test at a time.

## What runs where

- `just test`: every `tests/test_*.lua`, then `test_bake.py`, `test_lint.py`, `test_tools.py` and `test_tools_matrix.py` (the measuring tools' own tests; the second runs every call the tools document, and is not in `fast`).
- Pre-push (`tools/test.sh fast`): core, grow, leaf, letters, plant, settings, reserve, prepare_spec, render_page, inline, headpiece, row_phase, lint, tools and bake, each a few seconds at most. header_mark and support take minutes and run in CI instead (and under `just test`).
- CI (`.github/workflows/test.yml`): every test file, in fourteen groups of about five minutes each, and the table of calls and the raster test in jobs of their own. `tests/test_tools.py` fails when a `tests/test_*.lua` or `test_*.py` is run by no job (what a job runs is read from the workflow's text without its comments: the tests named to `tools/test.sh` or by path in a step that is not switched off with `if: false`, and a matrix group only when a step loops over the matrix's tests and gives each to `tools/test.sh`; any other condition is taken to hold, a matrix `include` or `exclude` is refused, and the paths filter that decides whether the workflow runs is checked by its own test), and when another file under `tests/` is neither one of the helpers and data it lists (with the reason) nor a test; a mutation of the workflow (a name taken out) is part of that test. The groups are dealt out from a run's times: run `just test-times 4` first (all tests must pass), then `python3 -I tools/test_times.py groups build/test-times.tsv 14 --skip tools_matrix`, and paste its lines into the workflow when the times have changed much. `build/test-times.tsv` is a link to the latest run and is not kept in the repository, so make the run you deal from; the present groups come from the run of 2026-11-26 (CPU seconds per group 308 to 341).

## Lint

`just lint` (`python3 -I tools/lint.py`) runs lua-language-server, ruff, shellcheck and pyright, as CI does (`.github/workflows/lint.yml`). ruff and pyright are taken from the repository's `.venv` before `PATH`; `just venv` makes it from `requirements-dev.txt`, which pins the versions CI installs, and pyright run from `.venv` resolves imports with `.venv`'s Python, where numpy and Pillow are. A tool that is missing fails the run with a line saying how to get it: pyright is no longer skipped locally. `tests/test_lint.py` runs `tools/lint.py` against stand-in tools for every way each can end, a tool in `.venv` before one on `PATH`, and an argument it does not take.

## Pages against pages

`python3 -I tools/page_diff.py A.pdf B.pdf [DPI] [OUT.png]` tells how far two renderings of a page differ: the share of pixels that change at all, the share that changes by more than 8 of 255 (what a reader might see), and the largest change, at DPI (300 by default); OUT.png shows where. It is the check for a change meant to leave a page looking as it did, where `just bodies-compare` asks for the same bytes. `just frame-flora timing OUT 11,11,11` times the vine and `surround` on each paper three times over (`pages.tsv`'s secs),; `just frame-flora density` and `stem` show the vine at each `perimeterdensity` and its stem, and `densitywidth` the narrowest bands at each.

## Hints

`just lint` fails on lua-language-server's findings from Warning up; the editor also shows Information and Hint (`.luarc.json` puts `duplicate-set-field` there). `just lint-hint FILE...` (`python3 -I tools/lint_hint.py FILE...`) runs the checker over the repository at the level Hint and prints the findings in the files named, a count for each and exit status 1 when there is any. Run it over the Lua files a change adds or edits; a test that replaces a module's field for a mutation does it through a helper with the field's name as a value (`t[key] = v`), which the checker does not take for a second definition.

## In Linux

CI runs Ubuntu, where `/bin/sh` is dash and the userland is GNU's (`time`, `xargs`; `awk` is mawk); a Mac runs bash as `sh` and BSD tools. `tools/test-linux.sh [ARGS]` (`just test-linux [ARGS]`) runs `tools/test.sh ARGS` (default: `fast`) in a container of CI's Ubuntu (24.04) with the packages CI installs (texlive-binaries, time) and those the runner brings that the tests use (python3, procps), from `tools/test-linux.Dockerfile`. The container runs the machine's own architecture; `FLORA_LINUX_PLATFORM=linux/amd64` runs CI's, emulated on another machine and many times slower (the fast set about 150 s against about 12 s natively on an Apple silicon Mac).

The container gets the tree CI checks out, as it stands in the working tree: the files git tracks and those it would track (untracked and not ignored), so uncommitted work is tried too, and nothing git ignores. A tracked file deleted in the working tree is not sent, and a symlink goes as the link. `tools/test-linux.sh --list` prints the files it sends, and `tests/test_tools.py` checks that every file the tests name is among them. Nothing written inside comes back.

It needs docker. The first run for an architecture builds its image (under a minute natively, several minutes emulated); `FLORA_LINUX_REBUILD=1` builds it again. Docker's virtual machine stops while the Mac sleeps, so a run's wall time across a sleep says nothing; time a run inside, with `--times`.

## Every documented call

The tools take their arguments in many forms, and each was once found wrong only in the call someone happened to make (`just test-times auto` lost its run; `tools/test.sh ""` ran every test; `--times` a directory moved the file into it). A call must either work or refuse in words, with a status other than 0, before it starts any test: none gives a traceback, fails silently, loses a measurement or ends with status 0 when it went wrong.

`tests/test_tools_matrix.py` holds the calls as a table (the rows of `CELLS`) and runs each one against stand-in tests in a temporary tree: `tools/test.sh` with every form of `-j` (omitted, 1, a number, `auto`, 0, a word, empty), of `--times` (omitted, a file, an unwritable path, empty, a directory) and of the test names (none, one, two, `fast`, unknown, twice, empty, failing, mixed), `tools/test_times.py` `show` and `compare` with every form of the file and of `--jobs`, `tools/profile.lua` with every option in its good and bad forms, and the justfile's recipes that call these (`just test`, `test-times`, `profile`, `test-linux`), and `tools/test-linux.sh` in docker. A recipe in the justfile that calls a tool and has no row fails the test, and so does one this page does not mention, so the table and the documentation stay together. Rows needing docker or just are skipped, with a line saying so, where it is missing. `TOOLS_MATRIX_TABLE=1 python3 -I tests/test_tools_matrix.py` prints the table with each call's expected and actual outcome and status. It takes about 25 s (50 s of CPU) with the container's rows, so it is not in `fast`; CI runs it as its own job (`.github/workflows/test.yml`). A step that fails after a measurement is made (the copy, the link, the report file) must leave the measurement, name where it is and end non-zero: rows inject those faults (a failing `cp` or `mv`, a target that is a directory or read-only, a report file that takes no data) and check it. A recipe that passes its arguments on (`profile`, `test-linux`, `test`, `test-times`, `bodies-compare`, `renderers-bench`) does so as `"$@"` (`set positional-arguments`), so that each stays one argument: `just profile -e 'print(1)'` works, and so does a script path with a space. Add a row when a tool gains an option. The rows for `tools/bodies-compare.sh` run against a stand-in `bodies.lua` in a one-commit git repository, since the real suites take minutes.

## When a run is stopped

A run ends in one of several ways (done, failed, an exception in a test, INT, TERM or HUP), and on none may a process it started stay running, those that the tools it started started in turn included. `tools/test.sh -j` and `--times` run the tests in a process group of their own and stop it as one, through `tools/toolproc.py stop-group` (TERM, a wait for the group to be gone, KILL for what is left, as everywhere else); a run of one test at a time runs it in the background and sends it the signal. Every trap in the shell tools ends with commands that cannot end the shell, so an interrupt always gives 128 plus the signal. `tools/test_times.py run`, `tools/lint.py` and the python tests of the tools start every program through `tools/toolproc.py`: it starts each in a session of its own, tracks it, and on INT, TERM or HUP (and atexit) sends the signal on to every one and to every other child of the process (listed with `/bin/ps`; where that cannot be run it stops the tracked groups, which needs no listing), waits up to 15 s (`TOOLPROC_GRACE`, in seconds, sets it) so that a supervisor like `tools/test.sh` can stop its tests, kills what did not obey, and ends with 128 plus the signal. `tools/test-linux.sh` names its container and kills it, and takes a signal during the file list and the image build too. A command run through the helper that outlives its timeout is stopped the same way, TERM first. `tests/test_tools.py` fails if one of those programs calls `subprocess` or starts a session or group of its own anywhere else. The table of calls interrupts a run of the tools' tests (which start runs of their own) with each signal, once a test below it sleeps, and requires the status 128 plus the signal and that none of the processes below it is left after ten seconds, and the same for `tools/test.sh` one test at a time, `tools/test_times.py run` and, with docker, `tools/test-linux.sh`. The older tools in `tools/` that are run by hand from a terminal (the `pattern-*.sh` and `edge*-sheets.sh` scripts, `grow.sh`, `bake_tune.py` and `tuner/server.py`) are stopped by the terminal's signal to their group, as before.

## Heavy tests, split

The three pattern matrices (the perimeter band's, the field reach's and the colour matrix's) were one file each and 636 to 947 CPU seconds, a floor under the wall time of any run with enough jobs. Each is now a suite (`tests/pattern_perimeter_suite.lua`, `pattern_reach_suite.lua`, `pattern_matrix_suite.lua`) that a few small files run in parts (`test_pattern_perimeter_1.lua` to `_4`, `test_pattern_reach_1` to `_3`, `test_pattern_matrix_1` to `_4`), each part with its share of the patterns and of the mutations (`tests/split.lua`: the items are dealt out by their weights in CPU seconds, heaviest first, to the lightest part; an item the plan does not weigh is an error, and a part says so when nothing in the suite asks for an item it was given). Every item runs in exactly one part, and a check that every part makes on its own share (the cells it swept) is counted once, in part 1, and reported by the others only when it fails: the parts together make the checks the whole made, which `FLORA_COUNT_CHECKS=1` shows (`H.checks` in `tests/helper.lua`), and `FLORA_SPLIT_LIST=1` names each item a part runs. When a pattern or a mutation is added to a suite, give it a weight there.

Flora in the perimeter band (`frames.lua`'s vine) has a suite of its own, `tests/perimeter_flora_suite.lua`, run in four parts (`test_perimeter_flora_1.lua` to `_4`) over `tests/perimeter_flora.lua`'s sweep: three papers, band widths of 6, 8, 12 and 18 mm, with and without a frame title, light and dark, each cell with a seed, an edge (none or `border`), a density (`perimeterdensity`) and a form (`perimeterflora`) dealt in turn, and two pages whose band is too narrow for flora. Its invariants are read from the painter's output, since the plants are cut to the band by a clip: the band is the pattern band's and the clip is that band; nothing paints outside the clip but the clips round it and the rule; the band holds the text block and its gap and every reservation is cut out; every side has paint in the band, the top under a frame title included, and no other clip cuts it; `edge=border` draws its rule and no other edge does; no frame carries a running head; each density is laid as asked, or in a band too narrow for it as the next denser one, saying so once; each form is laid with all its frames (vine 2, pinwheel 2, corners 8) or, where `corners` has no room for its arms, as the vine with a line in the log; and a band under 6 mm has no flora and says so once. A layout-only check (`F.layout`, the frames and the log without painting) runs that over every paper and a small one, both title modes, every form and density, every band from 6 to 40 mm in steps of 1 mm and uneven margins; the sweep's dealing is checked to ask every form at every density (`F.unasked`); and each form has a wide cell in the sweep (16:9 at 30 mm, 4:3 at 40 mm, about 70 CPU seconds in all) Each invariant has a mutation that breaks the engine the way it guards against (the plants left uncut, a wider band, one plant of the vine or of the pinwheel left out, one plant or one side's vine of corners left out, corners' arms left short, the fall back not said, the dealing put in step again, flora in narrower bands, no rule, the header clip back, a running head, a reservation not cut out, the gap round the text left out, `sparse` let into narrow bands), on one page each; the sweep's items and the mutations are weighed in CPU seconds, each item timed alone. `texlua tools/weigh_perimeter_flora.lua PAPER` times the sweep's items for a paper; a change in what the forms draw moves them, so weigh again then.

## Two runs at once

Several people, or several agents, run tests on one machine, so nothing the tools use may be shared between two runs. `tools/test.sh` keeps each run's files in a directory of its own (`mktemp -d`) and stops only the process group it made; `--times FILE` is made whole in that directory and copied to FILE at the end, and the directory stays, and is named, when the copy fails; `tools/test-linux.sh` sends a list from `mktemp` and starts an unnamed container. The one shared name is the image, built from the same recipe by whichever run finds it missing, and the link `build/test-times.tsv`, which points at the last run to finish (each run's own file stays). A test of the tools finds the processes it started by the pid they record, never by their command line, and `tests/test_tools.py` runs two copies of the runner's tests at once beside an unrelated process that has the command line of its sleepers, and requires that both pass and that the process is left alone.

## Timing

`tools/test.sh --times FILE` writes one tab-separated line per test: its name, exit status, and wall, user, sys and CPU (user + sys) seconds, most CPU first; the last line records the jobs, the time (UTC) and the machine's load average when the run ended. `just test-times [JOBS] [NAMES]` (JOBS a number or `auto`; `python3 -I tools/test_times.py run JOBS [NAMES]` is what it runs) runs it (default 4 jobs, every test) to a file of its own, `build/test-times/STAMP-PID.tsv`, with the run's output beside it as `.out`, shows it, and points `build/test-times.tsv` at it with a link. Nothing deletes a times file: `build/` can be emptied by hand when the old runs are not wanted. If the link cannot be made, or the file cannot be saved, the run says where the times are and exits non-zero:

```
python3 -I tools/test_times.py show build/test-times.tsv
python3 -I tools/test_times.py compare old.tsv new.tsv
```

A test that failed has its exit status in the file (one killed by a signal 128 plus the signal's number) and one without recorded times has NA. `tools/test_times.py` refuses a file that is empty, lacks its header or its closing line, or has a line that is not a test's times, naming the line; it marks failed and untimed tests and leaves them out of the totals and the schedule.

`show` prints the table with each test's share of the CPU and the least wall time some numbers of jobs could take on those CPU times (longest test first on the first free job; never less than the longest test). `compare` prints each test's CPU seconds in two runs and the change, and totals only the tests both runs timed and passed, naming the ones it left out (only in one run, failed, untimed).

`python3 -I tools/test_times.py groups build/test-times.tsv N [--skip TESTS]` deals the tests out to N groups of near equal CPU time (the heaviest first, each to the lightest group so far), one line a group; it needs a run in which every test passed. The test workflow's groups are made with it.

Compare CPU time, not wall time. Wall time depends on what else the machine runs (the load average in the file says how much), and tests run side by side share the machine too. Even CPU time moves by some per cent with load (shared caches, clock speed), so a change of a few per cent needs repeated runs to be believed; a count that does not depend on the machine (pages painted, calls made, below) settles it better.

## Profiling

`tools/profile.lua` runs a Lua script, or a chunk given with `-e`, and reports where it spent its time. `just profile ARGS` is `texlua tools/profile.lua ARGS`.

```
texlua tools/profile.lua tests/test_pattern_perimeter_1.lua
texlua tools/profile.lua --period 50000 --top 40 --out build/prof.txt tests/test_pattern.lua
texlua tools/profile.lua --time flora.pattern.clearance,flora.compose.page tests/test_pattern_matrix_1.lua
texlua tools/profile.lua --no-sample --time flora.compose.page -e 'dofile("my_bench.lua")'
```

Sampling (the default) notes the running function and its stack every `--period` virtual-machine instructions (10000 by default; larger is lighter on the run and coarser). The report has three tables: by function alone ("self"), by function with everything it calls ("inclusive"), and by line. The shares are of instructions run, not of seconds: time spent in C (building strings, allocating tables, the garbage collector, `string.format`) counts to the Lua line that asked for it, so a line that allocates in a loop shows up as that line. Under sampling a run takes some per cent longer.

`--time MODULE.FN,...` wraps the functions named and counts, exactly, each one's calls and its CPU seconds (callees included; a call nested in another of the same function is counted but not timed twice). It is the check on what the sampling points at, and it gives the counts (calls per page, pages per test) that do not depend on the machine's load. A function must be reached through its module's table (`Pattern.clearance`, not a local copy) to be counted.

The report is written when the script ends, by `os.exit` or an error too, so a failing test still reports, and its first line says which: completed, ended by os.exit(N) or stopped by an error. A timed function that raises an error is timed to the error and the report says how many of its calls raised; the error goes on as the same value (a pcall round it catches what it would have caught), but a traceback taken outside starts at the profiler's wrapper. Recursive calls are timed once, at the outermost; calls nest by coroutine, and a call's time includes any time it lies suspended in a coroutine. Coroutines the script creates are sampled too. A bad option, a `--time` name that does not resolve to a function, or an `--out` file that cannot be written stop the run before it starts (exit status 2).

## Byte for byte

`tools/bodies-compare.sh REF [SUITE...]` (`just bodies-compare REF [SUITE...]`) tells whether the working tree paints what commit REF painted, byte for byte. REF's tree is unpacked with git archive into `build/bodies.XXXXXX/ref`, a directory of the run's own (two runs at once do not share one), and both sides run `tools/bodies.lua` from the working tree, at once through `tools/toolproc.py run-all` (which waits for both, stops the other as soon as one fails, and stops both when the script is interrupted), with the working tree's slide fixtures; uncommitted changes count. It writes `ref.txt` and `new.txt` there, one line per page (suite, name, md5 of the body), prints the lines that differ and fails when any do, keeping the directory then (and when a side fails to paint), else removing it. A change meant to paint some pages anew is compared with `--expect FILE` (`just bodies-compare --expect FILE REF`): each line of FILE, blank lines and those starting with # aside, is an extended regular expression matched against a page's suite and name (`bands flora 16:9 8 false`), and the comparison ends with status 0 when exactly the pages some line matches differ and every other page is identical, and with 1, naming each page against the expectation, when a page differs that no line matches or one that a line matches is identical. It needs git, a git working tree and texlua, and refuses with a message (exit status 2) without them or when REF is not a commit; so it does not run in `tools/test-linux.sh`'s container, which has neither git nor the history.

The suites (`tools/bodies.lua` describes each): `bands`, 366 pages: 350 pattern pages of the perimeter band and of fields in three layouts, and 16 of flora in the perimeter band in its three forms; `slides`, 160 pages from four slide layouts LuaLaTeX measured (`tests/fixtures/slides`, written by `FLORA_SPEC_DIR`) in five layouts and eight settings, flora among them, painted one after another as in a document so that state one page leaves for the next shows; `progression`, twenty-one growth plans' eight stages each (flora in the perimeter band in its three forms among them); `protect`, the protect sweep's cells and failures. Each suite starts from no PDF resources, so rows added to one suite do not rename the resources the next one paints with. All four take some minutes, the progression suite the most. A suite compares the trees as they are: a change to `tests/pattern_perimeter.lua`'s page builder or `tests/pattern_protect.lua` changes what those suites paint too.
